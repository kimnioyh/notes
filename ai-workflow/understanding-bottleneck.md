# Understanding is the new bottleneck (Geoffrey Litt, Notion)

**한 문장**: AI 에이전트가 코드를 대신 짜주는 시대의 진짜 병목은 *코드 작성*이 아니라 **사람이 그 결과를 이해하는 것**이며, 정확성만 검증하고 이해를 건너뛰면 "cognitive debt"가 쌓인다.

## 왜 헷갈렸나

에이전트에게 맡기면 빨라진다고만 생각했는데, "그럼 사람은 뭘 하나?"가 안 잡혔다. 자율 루프(autonomous loop)가 다 해줄 것 같지만, 발표는 **대부분의 실무 에이전트 작업엔 여전히 인간의 판단이 필요**하고, 그 판단의 전제가 "이해"라고 짚는다. 즉 병목이 타이핑에서 이해로 옮겨간 것.

## 핵심

- **병목의 이동**: 코드를 쓰는 속도가 아니라, 에이전트가 만든 걸 사람이 이해하는 속도가 전체 속도를 정한다.
- **검증 ≠ 이해**: "테스트 통과 = 정확"만 보고 넘기면, 이해 못 한 코드가 부채로 쌓인다("cognitive debt"). 이해해야 다음 판단(리뷰·방향 설정)이 가능.
- **에이전트 코드를 이해하는 3가지 방법** (발표 요약 슬라이드 "How I understand agent code"):
  1. **Code explainers** — 코드의 배경·의도를 에이전트가 글로 설명하게 시킨다 (예: "이 엔진은 Phaser 3, flat canvas…" 배경 설명).
  2. **Quizzes** — *내가* 그 변경을 이해했는지 객관식 문제로 스스로 테스트한다 (슬라이드에 실제 4지선다 이해 점검 문제가 나옴).
  3. **Micro-worlds** — 코드 동작을 인터랙티브하게 탐험하는 작은 환경 (프로그램·스택 상태 시각화 등).
- 실무 도구로 언급된 **explain-diff**: diff/PR을 받아 "무엇이·왜 바뀌었나"를 설명 → 리뷰 전에 이해부터.
- 태도: 에이전트를 블랙박스로 두지 말고 각 단계를 이해하며 참여하는 **"상호 도제(mutual apprenticeship)" 루프**.

## 예시 코드

이 학습 노트 시스템(`/note`)에 실제로 반영한 지점 — 발표의 **Quizzes**를 노트 템플릿의 `## 확인 문제`로 채택:

```markdown
## 확인 문제
이 개념을 한 문장으로 설명해보라.

<details><summary>답</summary>
...
</details>
```

- Code explainers ≈ 노트 본문(핵심/예시)
- explain-diff ≈ 로드맵의 `/note --diff`
- Micro-worlds ≈ 런타임 시각화라 마크다운 노트 범위 밖 → 미채택

## 확인 문제

1. "이해가 새로운 병목"이라는 말에서, 무엇이 무엇으로 대체되어 병목이 옮겨간 것인가?
2. 정확성 검증(테스트 통과)만으로 충분하지 않은 이유는?
3. 발표가 제시한 "에이전트 코드를 이해하는 3가지 방법"은?

<details><summary>답</summary>

1. 병목이 **코드 작성 속도**에서 **사람이 에이전트 산출물을 이해하는 속도**로 옮겨갔다. 타이핑은 AI가 대신 하니 더는 제약이 아니다.
2. 테스트는 "동작이 맞는지"만 보장할 뿐, 왜 그렇게 짜였는지·다음에 뭘 바꿔야 하는지에 대한 **판단의 근거(이해)**를 주지 않는다. 이해 없이 통과만 시키면 cognitive debt가 쌓인다.
3. **Code explainers**(배경·의도 설명), **Quizzes**(이해 자가 점검), **Micro-worlds**(동작 인터랙티브 탐험).

</details>
