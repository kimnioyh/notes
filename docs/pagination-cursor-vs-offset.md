# 페이지네이션: 커서 vs offset, 그리고 봉투 seam

**한 문장**: offset 방식은 "N개 건너뛰고 M개"라 실시간으로 데이터가 쌓이면 중복/누락이 나고, 커서 방식("마지막 본 ID 다음부터")은 그걸 피하지만 클라가 커서를 왕복시켜야 한다.

## 왜 헷갈렸나
"페이지네이션 나중에 도입하면 공수 많이 드나? FE도 뭘 보내야 하나?"가 애매했다.

## 핵심

**offset 방식** — `?offset=20&limit=20` ("20개 건너뛰고 20개")
- 단순. 페이지 번호로 점프 쉬움.
- **실시간 피드엔 부적합**: 조회 사이 새 항목이 앞에 끼면 경계가 밀려 **중복/누락**. (소감처럼 계속 쌓이는 목록)

**커서 방식** — `?cursor=<마지막 본 ID>&limit=20` ("이 ID 다음부터 20개")
- `WHERE id < :cursor ORDER BY id DESC LIMIT :n`
- 새 항목이 끼어도 **안정적**(ID 기준이라 경계 안 밀림). 실시간 피드엔 이게 맞음.
- 대신 클라가 **이전 응답의 커서를 다음 요청에 넘겨야** 함(상태 관리).

**양쪽 계약 비용**: 페이지네이션은 FE가 (1) 요청 파라미터 추가, (2) 응답이 배열→봉투로 바뀜, (3) 더보기 루프. 그래서 규모 작으면 **YAGNI**.

**봉투 seam (비파괴 확장 지점)**: 지금 페이지네이션 안 하더라도, 목록 응답을 **`{ items: [...] }` 봉투**로 감싸두면 나중에 `nextCursor`/`hasMore`를 **필드 추가**만으로 도입 가능(맨 배열→봉투 breaking 회피). FE는 처음부터 `.items`로 언랩.

## 예시 코드
```jsonc
// 지금 (v1): 봉투만, 페이지네이션 없음
{ "items": [ /* Event[] */ ] }

// 나중: 비파괴적으로 필드만 추가
{ "items": [ ... ], "nextCursor": "1234", "hasMore": true }
```
```java
// 나중 커서 쿼리 (Spring Data)
List<Feedback> findByEventIdAndIdLessThanOrderByIdDesc(Long eventId, Long cursor, Limit limit);
```

## 확인 문제
1. 실시간으로 소감이 계속 쌓이는 목록에 offset 페이지네이션을 쓰면 무슨 문제가 나나?
2. 지금 페이지네이션을 안 하는데도 목록을 `{items:[]}`로 감싸는 이유는?

<details><summary>답</summary>

1. 조회하는 사이 새 소감이 목록 앞쪽에 삽입되면 offset 경계가 한 칸씩 밀려서, 이미 본 항목을 **중복**해서 받거나 어떤 항목을 **건너뛰는(누락)** 일이 생긴다. 그래서 실시간 피드엔 ID 기준 **커서**가 맞다.
2. 나중에 페이지네이션을 넣을 때 응답 모양이 "맨 배열 → 객체"로 바뀌는 게 **유일한 breaking 변경**인데, 미리 봉투로 감싸두면 `nextCursor`/`hasMore`를 **필드 추가**(비파괴)만으로 도입할 수 있다. FE는 계속 `.items`만 읽으면 됨.

</details>
