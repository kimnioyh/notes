# D5 정리 — 결제 서버 승인(confirm) · 멱등성 · 결제 도메인 개념

> 대중교통용 요약. 개념 → 왜 → 우리 코드 순서. 면접에서 "설명할 수 있는" 수준이 목표.
> 핀테크(결제) 도메인이 이 프로젝트의 차별화 축 → 이 문서 개념들이 곧 면접 무기.

---

## 0. 한 문장 정리

- **결제창 성공 ≠ 결제 완료.** 사용자가 결제창에서 성공해도, **서버가 토스에 "이 결제 승인해"라고 confirm을 호출해야** 실제로 돈이 움직이고 완료됨.
- 그래서 흐름이 **2단계**: ① 결제창 열기 전에 서버가 주문(PENDING) 생성 → ② 성공 후 서버가 승인(confirm) → DONE.
- 이 과정에서 지켜야 할 3원칙: **멱등성 · 금액 위변조 검증 · 키 분리(client/secret)**.

---

## 1. 왜 "서버 승인(confirm)"이 따로 필요한가

토스 결제창에서 "성공"이 떠도 그건 **"결제 요청이 접수됨"**일 뿐, 아직 승인 전이야.
결제창은 그저 사용자가 카드정보를 넣는 UI고, **실제 매입(돈 이동)은 가맹점 서버가 승인 API를 호출**해야 일어남.

왜 이렇게 나눠놨나?
- **보안**: 승인은 `secretKey`가 필요한데, 이건 절대 브라우저에 두면 안 됨 → 서버만 가능.
- **검증 기회**: 승인 직전에 "이 주문 우리가 만든 거 맞아? 금액 안 바뀌었어?"를 서버가 확인할 수 있음.
- **정합성**: 결제창은 성공했는데 우리 DB엔 기록이 없는 상황을 방지 → 승인과 저장을 서버가 같이 처리.

> 면접 한 줄: **"결제창 성공은 접수, 실제 완료는 서버 confirm. 승인 전에 서버가 금액·주문을 검증한다."**

## 2. 멱등성 (Idempotency) — 이번 핵심

### 개념
**같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같음.**
수학의 `f(f(x)) = f(x)`. 결제에선 **"승인 요청이 2번 가도 결제는 1번만 되어야 한다"**.

### 왜 결제에서 특히 중요한가
결제는 **중복되면 진짜 돈이 두 번 빠지는** 도메인이라, 중복은 버그가 아니라 **사고**야.
그리고 중복 요청은 생각보다 흔해:
- 사용자가 성공 페이지를 **새로고침(F5)**
- **더블클릭**, 뒤로가기 후 재진입
- 네트워크 타임아웃 → 클라가 **재시도**(응답을 못 받았을 뿐 서버는 성공했을 수도)
- React 개발모드의 **이펙트 2회 실행**

→ 이 모든 경우에 "두 번째 요청"이 와도 **두 번째 결제가 일어나면 안 됨**.

### 멱등키 (Idempotency Key)
"이 요청은 저 요청과 같은 건이다"를 식별하는 열쇠. 우리는 **`orderId`**가 그 역할.
DB에서 `orderId @unique` → 같은 orderId로는 결제가 하나만 존재. 이게 멱등성의 물리적 보장.

### 우리 코드에서 (lib/payments.ts)
```ts
// ① orderId로 주문 조회 (없으면 우리가 만든 게 아님 → 거부)
const payment = await prisma.payment.findUnique({ where: { orderId }, ... });
if (!payment) return { ok: false, reason: "존재하지 않는 주문" };

// ② 이미 승인(DONE)된 건이면 → 토스 재호출 없이 그대로 성공 반환  ★ 멱등의 핵심
if (payment.status === "DONE") {
  return { ok: true, orderName: ..., amount: payment.amount };
}
```
두 번째 confirm이 와도 `status === "DONE"`에서 걸려 **토스를 다시 부르지 않음** → 이중 결제 원천 차단.

### ★ 가드 "순서"가 왜 중요한가 (D5에서 직접 겪은 것)
```
1) DONE이면 → 성공 반환      (멱등 가드)   ← 먼저
2) 금액 다르면 → 거부         (금액 가드)   ← 나중
```
이미 정산 끝난(DONE) 결제는 **금액을 다시 검증하지 않음**. 완료된 거래는 완료된 것.
금액 검증은 **PENDING → DONE로 넘어가는 그 순간**만 지키면 됨.
> 그래서 "이미 성공한 창에서 amount만 바꿔 새로고침" → 여전히 성공 뜸(멱등 가드가 먼저). **버그가 아니라 정상.**
> 금액 가드를 보려면 **아직 PENDING인 주문**에 틀린 금액을 먹여야 함.

> 면접 한 줄: **"orderId를 멱등키로 unique 제약 + DONE 조기반환으로 이중 결제를 막았다. 멱등 체크를 금액 체크보다 먼저 둬서, 완료된 결제는 재검증하지 않고 검증은 미확정 결제에만 적용된다."**

## 3. 금액 위변조 검증 (신뢰 경계)

### 개념
클라이언트(브라우저)가 보내는 값은 **사용자가 조작할 수 있음** → 절대 그대로 믿지 않음.
결제창/리다이렉트 URL의 `amount`는 사용자가 손댈 수 있으니, **서버가 미리 확정해둔 금액과 대조**해야 함.

### 그래서 2단계로 만든 이유 (이게 핵심 설계)
- **1단계(결제 시작)**: 결제창 열기 **전에** 서버가 구독을 조회해 **amount를 확정**하고 PENDING으로 저장.
  → 서버 DB에 "진짜 금액"이 박혀 있음 (신뢰의 원천).
- **2단계(승인)**: 리다이렉트로 온 `amount`를 **DB의 확정 금액과 비교** → 다르면 거부.

```ts
// route.ts (1단계) — 서버가 amount를 확정
const sub = await prisma.subscription.findUnique({ where: { id: subscriptionId } });
await prisma.payment.create({ data: { subscriptionId, amount: sub.amount, orderId } });

// payments.ts (2단계) — 확정 금액과 대조
if (payment.amount !== amount) return { ok: false, reason: "결제 금액 불일치" };
```
만약 결제창 열 때 클라가 준 amount를 그냥 저장했다면? 사용자가 1000원짜리를 1원으로 바꿔 결제해도 통과됨.
→ **금액은 반드시 서버가 정한다.**

> 면접 한 줄: **"금액은 클라가 아니라 서버가 구독 정보로 확정해 PENDING에 저장하고, 승인 때 그 값과 대조해 위변조를 막는다 = 신뢰 경계."**

## 4. 키 분리 — clientKey vs secretKey

| 키 | 위치 | 용도 | 노출 |
|---|---|---|---|
| `clientKey` (`NEXT_PUBLIC_`) | 브라우저 | 결제창 열기 | 노출 OK |
| `secretKey` (접두사 없음) | 서버만 | 결제 **승인**(confirm) | **절대 금지** |

- `NEXT_PUBLIC_` 접두사가 붙은 것만 브라우저 번들에 포함됨 → `secretKey`엔 안 붙임.
- confirm은 **서버 컴포넌트/Route Handler**에서만 → secretKey가 브라우저로 샐 일이 없음.
- 토스 인증: `Authorization: Basic base64(secretKey + ":")` (비밀번호 없는 Basic Auth).

> 면접 한 줄: **"공개키(clientKey)는 결제창용, 비밀키(secretKey)는 서버 승인용. NEXT_PUBLIC 접두사로 노출 경계를 코드 레벨에서 강제했다."**

## 5. 상태 머신 — PENDING / DONE / FAILED

결제 1건은 상태를 따라 움직임. 상태를 명시적으로 저장해두면 "결제창은 성공했는데 승인이 안 된" 애매한 건도 추적 가능.

```
        결제 시작            토스 confirm 성공
[없음] ──────────▶ PENDING ──────────────────▶ DONE
                     │
                     │ confirm 실패(토스 거절/금액불일치)
                     └────────────────────────▶ FAILED
```
- **PENDING**: 주문은 만들었지만 아직 승인 전 (사용자가 결제창 닫고 안 돌아오면 여기 머묾).
- **DONE**: 승인 완료. `paymentKey`, `approvedAt` 채워짐.
- **FAILED**: 토스가 거절하거나 검증 실패.

`amount`는 `Int`(원 단위 정수)로 저장 → **부동소수 오차 방지**(결제 도메인 정석. `0.1 + 0.2 !== 0.3` 같은 사고 예방).

## 6. 리다이렉트 흐름 & 부수효과 (알아둘 것)

우리 성공 페이지는 **서버 컴포넌트**라, 토스가 리다이렉트하면 렌더 중에 바로 `confirmPayment`를 호출함.
- 장점: secretKey 서버 전용과 딱 맞고, 클라 상태머신 없이 간단.
- 주의: **GET 렌더 중 부수효과(승인)** → 새로고침하면 다시 실행됨 → 그래서 **멱등 처리가 필수**(2번 절과 연결).

### 실무에서 한 걸음 더: 웹훅 (면접 "다음 개선" 소재)
리다이렉트만 믿으면 구멍이 있음: **사용자가 결제창 성공 직후 브라우저를 꺼버리면** 우리 서버는 승인 호출을 못 함 → 돈은 걸렸는데 DB는 PENDING인 불일치.
→ 실무는 **웹훅(webhook)**을 병행: 토스가 우리 서버로 직접 "이 결제 상태 바뀜"을 통지 → 리다이렉트가 유실돼도 서버가 상태를 맞춤.
우리 프로젝트는 범위상 리다이렉트+confirm까지만 (웹훅은 "확장 포인트"로 언급하면 좋음).

> 면접 한 줄: **"리다이렉트 기반 confirm은 사용자가 창을 닫으면 유실될 수 있어, 실무에선 웹훅으로 서버-투-서버 통지를 병행해 정합성을 보강한다."**

## 7. 전체 흐름 (우리 D5)

```
[구독 목록] "결제" 클릭
  │  PaySubscriptionButton (usePayment 훅 직접 사용)
  ▼
① POST /api/payments   ← 서버가 amount 확정 + orderId 발급 + PENDING 저장
  │  { orderId, amount, orderName } 반환
  ▼
requestPayment(...)  → 토스 결제창 오픈 → 사용자 결제
  ▼
토스가 /payment/success?paymentKey&orderId&amount 로 리다이렉트
  ▼
② confirmPayment (서버 컴포넌트)
  │  - orderId로 PENDING 조회 (없으면 거부)
  │  - DONE이면 그대로 성공 (멱등)
  │  - 금액 대조 (위변조 검증)
  │  - 토스 confirm 호출 (secretKey)
  │  - 성공 → DONE + paymentKey + approvedAt
  ▼
결과 표시 → /subscriptions 결제 내역에 반영
```

## 8. 면접 예상 질문 셀프체크

1. 결제창 성공 = 결제 완료? → **아님.** 접수일 뿐, 서버 confirm 호출이 있어야 완료.
2. 멱등성이란? → 같은 요청 여러 번 = 한 번과 같은 결과. 결제 중복 = 이중 인출 사고라 필수.
3. 멱등을 어떻게 보장? → `orderId`를 멱등키로 `@unique` + DONE 조기반환으로 토스 재호출 차단.
4. 왜 멱등 체크가 금액 체크보다 먼저? → 완료된 결제는 재검증 대상이 아님. 검증은 미확정(PENDING) 건만.
5. 금액 위변조를 어떻게 막나? → 결제창 전에 서버가 금액을 확정·저장 → 승인 때 대조. 클라 값 불신 = 신뢰 경계.
6. clientKey vs secretKey? → 공개키(결제창)/비밀키(서버 승인). NEXT_PUBLIC로 노출 경계 강제.
7. 왜 2단계(PENDING→DONE)? → 승인 전 검증 기회 확보 + 결제창 성공/서버 기록 불일치 방지.
8. 리다이렉트의 약점과 보완? → 사용자가 창 닫으면 유실 → 실무는 웹훅 병행.
