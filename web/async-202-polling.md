# 비동기 API — 202 Accepted + 폴링

**한 문장**: 오래 걸리는 작업은 서버가 **202로 "접수했고 처리 시작함"만 즉시 응답**하고, 완료는 서버가 한 번 더 보내주는 게 아니라 **클라가 GET으로 다시 조회(폴링)**해서 확인한다 — HTTP는 요청 하나에 응답 하나뿐이라.

## 왜 헷갈렸나
"202를 보내고 나중에 완료 응답을 한 번 더 보내는 건가?"가 안 잡혔다. HTTP는 **요청-응답이 1쌍**이라 한 요청에 응답을 두 번 못 보낸다. 202를 보내는 순간 그 요청은 끝이고, 서버가 클라에게 먼저 말을 걸지도 않는다(클라가 물어봐야 답하는 구조).

## 핵심

### 1. 202 Accepted = "접수, 아직 안 끝남"
- "요청 받았고 처리는 시작했는데 결과는 아직. 나중에 딴 데서 확인해." 응답 한 번 주고 연결은 끝.
- 왜 필요? 실제 작업(LLM 호출 등)이 몇 초 걸리는데 요청 스레드를 붙잡으면 안 되니까. 즉시 202로 놓아주고 백그라운드로 넘긴다.

### 2. 완료 확인 = 클라가 다시 물어본다(폴링)
```
클라 → POST .../generate
서버 → 202 (status: GENERATING)     [요청 끝, 연결 닫힘]
       ┄ 백그라운드 처리 ┄
       DB: status = GENERATED 로 갱신
클라 → GET .../report                (조금 뒤 다시 조회)
서버 → 200 (status: GENERATING)      아직...
클라 → GET .../report
서버 → 200 (status: GENERATED ✅)    완료!
```
서버가 "완료를 한 번 더" 보내는 게 아니라, 클라가 GET을 주기적으로 반복해 `GENERATING → GENERATED` 전이를 본다.

### 3. 폴링 vs push(SSE/웹훅)
- **폴링**(기본): 클라가 반복 조회. 단순하고 어디서나 동작. 지연·낭비 요청이 단점.
- **SSE/웹훅**: 서버가 완료를 능동 통지. 실시간이지만 연결 관리·인프라가 필요. 기본은 폴링.

### 4. 스텁이면 비동기가 필요 없어질 수도
느린 작업이 없으면(예: LLM을 즉시 반환 스텁으로) 202·폴링을 생략하고 동기로 한 방에 끝내도 된다. 비동기는 "느린 작업"용이지 목적이 아니다.

## 예시 코드
Pulse 리포트 생성 — LLM 요약이 오래 걸릴 것을 전제로 비동기:
```
POST /events/{code}/report/generate → 202, Report(status=GENERATING)
   (백그라운드 워커가 집계+요약 채워 GENERATED로 갱신)
GET /events/{code}/report → 폴링으로 GENERATING → GENERATED 확인
```
Feedback 실시간 집계도 같은 폴링 원리(FE가 `GET /feedbacks`를 주기 호출).

## 확인 문제
1. 서버가 202를 보낸 뒤 "완료 응답을 한 번 더" 보내지 못하는 이유는? 완료는 어떻게 확인하나?
2. LLM 요약을 즉시 반환 스텁으로 두면 202·폴링 구조가 왜 필요 없어지나?

<details><summary>답</summary>

1. HTTP는 요청 하나에 응답 하나(요청-응답 1쌍)라 한 요청에 두 번 응답할 수 없고, 서버가 클라에게 먼저 연결을 열지도 않는다. 202로 접수만 알린 뒤, 클라가 상태 조회 엔드포인트(GET)를 주기적으로 다시 호출(폴링)해 완료로 바뀐 걸 확인한다(또는 SSE/웹훅으로 push).

2. 비동기(202+폴링)는 작업이 느려서 요청 스레드를 오래 붙잡지 않으려는 것이다. 스텁이 즉시 끝나면 붙잡을 시간이 없으니, 그냥 동기로 계산해 완성된 결과를 200으로 한 번에 반환하면 된다.

</details>
