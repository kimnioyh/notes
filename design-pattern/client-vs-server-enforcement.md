# 클라이언트 검증(UX) vs 서버 검증(보안)

**한 문장**: 같은 규칙이라도 **클라이언트 검증은 편의(UX) 안내라 우회 가능**하고 **서버 검증은 신뢰 경계의 강제**라, 목적이 달라 둘 다 두는 게 정상 — 클라는 사용자를 돕고, 서버는 클라를 안 믿는다.

## 왜 헷갈렸나
Pulse에서 "세션당 소감 1회"를 프론트가 막는데, 서버는 왜 또 "분당 3회" 레이트리밋을 두지? 중복 아닌가 싶었다. 답: **둘은 다른 것을 막는다.** 하나는 중복 제출 안내(UX), 하나는 도배/어뷰징 방어(보안). 그리고 FE 제한은 강제가 아니다.

## 핵심

### 1. 클라 검증은 "신사협정"이라 우회된다
- FE의 "세션당 1회"는 보통 `localStorage`에 제출 플래그를 찍어 버튼을 비활성화하는 **안내**다.
- `localStorage`를 지우거나, 시크릿창/다른 기기/스크립트면 그냥 뚫린다. **클라에서 하는 검증은 보안이 아니라 UX**다.

### 2. 서버는 클라를 신뢰하지 않는다
- 서버는 FE 안내를 무시하고 들어오는 요청을 전제해야 한다. 그래서 신뢰 경계(서버)에서 **강제**할 방어가 따로 필요하다.
- Pulse의 레이트리밋([[rate-limiting-sliding-window]])이 그 최후 방어선 — 중복 방지가 아니라 **속도 제한(스팸/DoS 컷)**.

### 3. 목적이 다르면 규칙도 다르다
| | 막는 것 | 위치 | 강제성 |
|---|---|---|---|
| 세션당 1회 | 중복 제출 혼란 | FE(localStorage) | 안내(우회 가능) |
| 분당 3회 | 도배/어뷰징 | 서버 | 강제 |

서버가 "1회"로 딱 잠그지 않는 이유: (1) 오타 수정·재제출 같은 **정상 재시도**까지 막고, (2) 서버가 "이미 냈는지" 상태를 안 들고 있어(중복 허용 설계) 1회 강제가 구조에 안 맞다. 그래서 "완전 차단"이 아니라 "도배 속도만 제한"으로 절충한 게 분당 3회.

### 4. 일반 원칙 — 다층 방어(defense in depth)
클라 검증(빠른 피드백·UX)과 서버 검증(진짜 강제)은 **역할이 겹치는 게 아니라 층이 다르다.** 폼 검증도 같다: FE의 `required`·형식 체크는 UX, 서버의 `@Valid`가 진짜 방어선. FE 검증만 믿고 서버 검증을 빼면 뚫린다.

## 예시 코드
Pulse 소감 제출: FE는 제출 완료를 localStorage로 안내(중복 방지 UX), 서버는 그와 무관하게 게이트+레이트리밋으로 강제.
```
[FE] localStorage "이미 냈음" → 버튼 disable   ← UX, 우회 가능
[BE] Event LIVE && Session ACTIVE 게이트         ← 강제
     (sessionId, clientId) 분당 3회 레이트리밋   ← 강제
```
명세서에도 못박음: "동일 세션 중복 제출은 서버가 막지 않습니다. 프론트엔드가 localStorage로 안내합니다."

## 확인 문제
1. FE가 "세션당 1회"를 막는데 서버에 레이트리밋을 또 두는 이유는? 두 규칙이 각각 막는 게 뭔가?
2. 서버가 중복을 "정확히 1회"로 강제하지 않고 분당 3회로 둔 이유 두 가지는?

<details><summary>답</summary>

1. FE의 1회 제한은 localStorage 기반 UX 안내라 지우거나 다른 기기/스크립트로 우회된다. 서버 레이트리밋은 그 우회를 노린 도배/어뷰징을 강제로 막는 별개 방어선이다. 전자는 중복 제출 혼란, 후자는 스팸/DoS를 막는다.

2. (1) 오타 수정·재제출 같은 정상 재시도까지 막히고, (2) 서버가 "이미 냈는지"를 상태로 안 들고 있어(중복 허용 설계) 1회 강제가 구조에 안 맞다. 그래서 도배 속도만 제한하는 절충으로 분당 3회.
